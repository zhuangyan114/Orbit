## ARMGCC

### 什么是ARMGCC

ARMGCC是一类总称,我们要使用的是arm-none-eabi-gcc \
**arm-none-eabi-gcc** 是用于 ARM 裸机开发的开源交叉编译工具链，可将 C/C++ 程序编译为适用于 ARM Cortex-M 等微控制器的可执行代码。

### 下载 ARMGCC

1. 从 Arm 官方下载 GNU Arm Toolchain。

   [官方下载链接](arm-gnu-toolchain-15.2.rel1-mingw-w64-x86_64-arm-none-eabi.zip)

   下载 Windows 64 位版本，例如：

   > arm-gnu-toolchain-15.2.rel1-mingw-w64-x86_64-arm-none-eabi.zip

2. 也可以下载 xPack 发布的 ARM GCC。

    [github下载链接](https://github.com/xpack-dev-tools/arm-none-eabi-gcc-xpack/releases/tag/v15.2.1-1.1)

   xPack 对官方 Arm GNU Toolchain 进行了重新打包，包含相同的 `arm-none-eabi-gcc` 编译工具链，可直接用于 STM32 开发。

   例如：

   > xpack-arm-none-eabi-gcc-15.2.1-1.1-win32-x64.zip

### 安装ARMGCC

1. 把解压后的文件夹放到C盘根目录

2. 设置环境变量

    设置>系统>系统信息>高级系统设置>环境变量,找到系统变量里的Path,双击进入编辑环境变量>新建
    把刚刚移到C盘的文件夹的bin的文件目录粘贴进去
    如:
    > C:\xpack-arm-none-eabi-gcc-15.2.1-1.1\bin

3. 验证

    在PowerShell里输入 `arm-none-eabi-gcc --version` ,有显示版本号即可

## CMake

### 什么是CMake

CMake 是一个用于管理和生成编译工程的工具。它本身通常不负责直接编译代码，而是根据工程中的配置文件，生成对应编译工具能够识别的构建文件。

简单来说，CMake 就像一份“编译说明书”。我们在 `CMakeLists.txt` 中告诉它：

- 工程中有哪些源文件；
- 需要搜索哪些头文件目录；
- 需要链接哪些库文件；
- 使用哪一种编译器；
- 最终生成什么类型的文件。

CMake 读取这些配置后，可以生成不同平台和不同构建工具所需要的文件，例如 Makefile、Ninja 构建文件或 Visual Studio 工程文件。这样，同一套工程配置就可以在不同环境下使用，不需要为每种编译器重新编写一套完整的编译命令。

在本教程中，CMake 主要负责组织 STM32 工程的编译流程，ARM GCC 负责真正编译和链接代码，最终生成可以下载到单片机中的程序文件，例如 `.elf`、`.hex` 或 `.bin` 文件。

可以把整个过程简单理解为：

```text
CMakeLists.txt
      ↓
    CMake
      ↓
生成编译规则
      ↓
  ARM GCC 编译
      ↓
生成 STM32 程序文件
```

因此，CMake 和 ARM GCC 是两个不同的工具：CMake 负责“安排怎么编译”，ARM GCC 负责“执行具体编译”。

### 下载CMake

1. 打开 CMake 官方下载页面：

   [CMake 官方下载页面](https://cmake.org/download/)

2. 在 **Latest Release** 中找到 Windows 版本，下载 Windows 64 位安装程序，文件一般类似于：

   > cmake-4.x.x-windows-x86_64.msi

   版本号会随着 CMake 发布而变化，下载最新的稳定版本即可。

### 安装CMake

1. 双击下载的 `.msi` 安装程序。

2. 安装过程中，如果看到添加环境变量的选项，选择将 CMake 添加到当前用户或所有用户的 `PATH` 中。

   如果没有选择该选项，也可以手动把 CMake 的 `bin` 目录添加到环境变量，例如：

   > C:\Program Files\CMake\bin

3. 安装完成后，关闭已经打开的 PowerShell 或 VS Code 窗口，再重新打开终端。环境变量只会对新启动的程序自动生效。

4. 在 PowerShell 中验证安装：

   ```powershell
   cmake --version
   ```

   如果能看到 CMake 的版本号，说明 CMake 已经安装成功。

   如果终端仍然提示找不到 `cmake`，可以直接使用完整路径验证：

   ```powershell
   & "C:\Program Files\CMake\bin\cmake.exe" --version
   ```

## CMake Tools

### 什么是CMake Tools

CMake Tools 是 VS Code 的扩展，用来在 VS Code 中方便地配置、编译和管理 CMake 工程。

它可以帮助我们选择编译器、选择 Debug 或 Release 构建类型、生成构建目录、执行编译以及查看编译错误。但是，CMake Tools 本身不是 CMake，也不包含 ARM GCC，仍然需要提前安装 CMake 和 ARM GCC。

### 安装CMake Tools

1. 打开 VS Code 左侧的扩展视图，或者按下快捷键：

   ```text
   Ctrl + Shift + X
   ```

2. 搜索：

   > CMake Tools

3. 选择发布者为 **Microsoft**、扩展标识为 `ms-vscode.cmake-tools` 的扩展并安装。

   [CMake Tools 官方仓库](https://github.com/microsoft/vscode-cmake-tools)

4. 安装完成后，重新加载 VS Code 窗口。

5. 打开包含 `CMakeLists.txt` 的工程文件夹，按下 `Ctrl + Shift + P` 打开命令面板，输入 `CMake`。确认能看到以下命令：

   - `CMake: Configure`
   - `CMake: Build`

   如果工程启用了 Presets，还会看到 `CMake: Select Configure Preset` 和 `CMake: Select Build Preset`。

   **不要用能否搜到 Kit 命令判断安装是否成功。** CMake Tools 支持 Presets 和 Kit 两种配置模式；启用 Presets 时，`CMake: Scan for Kits`、`CMake: Select a Kit` 和 `CMake: Select Variant` 会被隐藏。本教程优先使用工程提供的 `CMakePresets.json`。参见 [CMake Tools 官方 Presets 说明](https://github.com/microsoft/vscode-cmake-tools/blob/main/docs/cmake-presets.md#unsupported-commands)。

### CMake Tools的图形化界面

CMake Tools 不是单独的桌面软件，它把图形化操作界面集成到了 VS Code 中。安装完成后，打开包含 `CMakeLists.txt` 的工程，在左侧活动栏打开 **CMake** 视图，其中的 **Project Status（项目状态）** 可以查看和切换：

- 当前 Configure Preset（配置预设）；
- 当前 Build Preset（构建预设）；
- Configure 配置按钮；
- Build 编译按钮；
- 当前构建目标。

点击这些项目，就可以完成大部分常用操作。也可以使用 `Ctrl + Shift + P` 打开命令面板执行相同操作。

底部状态栏是否显示 CMake 按钮取决于扩展设置，没有按钮不代表安装失败。如果需要显示，可以在 VS Code 的 `settings.json` 中合并以下设置：

```json
{
    "cmake.options.statusBarVisibility": "visible"
}
```

Kit 模式的项目状态会显示 Kit 和 Variant；Presets 模式会显示预设，不需要再选择 Kit。

另外，CMake 官方还提供了一个独立的图形化程序 `cmake-gui.exe`。Windows 版 CMake 通常会同时安装它，可以在开始菜单中搜索 **CMake** 或 **CMake GUI** 打开。CMake GUI 主要用于选择源码目录、构建目录、生成器以及查看 CMake 缓存变量。

```text
CMake GUI       → 独立的 CMake 图形化程序
CMake Tools     → 集成在 VS Code 中的 CMake 图形化操作界面
```

对于本教程，推荐直接使用 CMake Tools，因为编写代码、配置工程和编译都可以在 VS Code 中完成。CMake GUI 不是必须安装的工具。

### 第一次配置CMake Tools

#### 1. 打开工程文件夹

不要只打开某一个 `.c` 文件，而是使用 VS Code 的“文件 → 打开文件夹”，打开包含 `CMakeLists.txt` 的工程根目录。

打开工程后，CMake Tools 会自动搜索 `CMakeLists.txt`，并尝试检测电脑上可用的 CMake 和编译器。

#### 2. 选择CMake路径

如果 CMake 已经加入环境变量，CMake Tools 通常会自动找到它。如果没有找到，可以在 VS Code 的 `settings.json` 中手动指定路径：

```json
{
    "cmake.cmakePath": "C:\\Program Files\\CMake\\bin\\cmake.exe"
}
```

也可以在命令面板中执行 `CMake: Configure`。如果 CMake 路径有问题，CMake Tools 会在输出面板中显示错误原因。

#### 3. 选择配置预设

先查看工程根目录是否有 `CMakePresets.json`。很多 STM32 CMake 工程已经提供该文件，其中保存了工具链文件、生成器、构建目录和 Debug / Release 等配置。

CMake Tools 的 `cmake.useCMakePresets` 默认值为 `auto`：在当前 CMake 源码目录找到 `CMakePresets.json` 时，自动使用 Presets 模式。因此，这类工程里搜索 `kit` 没有相关命令是正常现象。参见 [官方模式切换说明](https://github.com/microsoft/vscode-cmake-tools/blob/main/docs/cmake-presets.md#enable-cmakepresetsjson-in-the-cmake-tools-extension)。

按下 `Ctrl + Shift + P`，执行：

```text
CMake: Select Configure Preset
```

从列表中选择工程提供的 Debug 配置预设，名称可能是 `Debug`、`debug` 或其他名称，以实际工程为准。

对于 STM32 工程，应确认所选预设通过 `toolchainFile` 或 `CMAKE_TOOLCHAIN_FILE` 指向工程提供的 ARM GCC 工具链文件，而不是电脑本机的 MSVC 或 x86 GCC。工具链文件中配置的编译和格式转换工具通常包括：

```text
C 编译器：   arm-none-eabi-gcc.exe
C++ 编译器： arm-none-eabi-g++.exe
格式转换：   arm-none-eabi-objcopy.exe
```

如果预设使用 `Ninja` 生成器，还需要让 CMake Tools 能找到 `ninja.exe`。如果电脑上还没有可用的 Ninja，可以从 [Ninja 官方发布页面](https://github.com/ninja-build/ninja/releases) 下载 Windows 版本，将解压目录加入 `PATH`，重新打开 VS Code 后执行 `ninja --version` 验证。CMake 和 ARM GCC 的安装不等于已经安装了 Ninja。

如果工程没有预设文件，先按照下面“工程没有 CMakePresets.json”的说明补充配置。

#### 4. 确认Debug配置并选择构建预设

对于 STM32 工程常用的 Ninja 等单配置生成器，构建类型由配置预设中的 `CMAKE_BUILD_TYPE` 决定，不再执行 `CMake: Select Variant`。Debug 配置通常设置了 `"CMAKE_BUILD_TYPE": "Debug"`，也可能从父预设继承该设置。如果工程使用多配置生成器，则在构建预设的 `configuration` 字段选择 `Debug` 等构建类型。

常用构建类型如下：

| 构建类型 | 说明 |
| --- | --- |
| `Debug` | 保留调试信息，方便 Orbit 进行断点和源码调试 |
| `Release` | 开启更多优化，适合发布或测试最终性能 |
| `MinSizeRel` | 尽量减小程序体积 |
| `RelWithDebInfo` | 优化程序，同时保留调试信息 |

初次配置时建议选择 `Debug`，并确认工程的编译选项包含调试信息，否则生成的 ELF 文件可能缺少源码调试所需的 DWARF 信息。

然后执行：

```text
CMake: Select Build Preset
```

选择与当前配置预设对应的构建预设。构建预设的 `configurePreset` 应指向刚才选择的配置预设；配置预设和构建预设的名称不一定相同。如果工程没有定义构建预设，可以使用扩展提供的默认构建预设，按当前配置生成的构建目录编译。

#### 5. Configure配置工程

选择好配置预设后，执行：

```text
CMake: Configure
```

这一步会让 CMake 读取工程中的 `CMakeLists.txt`，检查编译器、头文件、库文件和构建选项，并在构建目录中生成 `CMakeCache.txt` 以及具体的编译规则。

构建目录由配置预设中的 `binaryDir` 决定，可能是 `build/Debug`，也可能是其他目录。例如，预设使用 `${sourceDir}/build/Debug` 时，配置成功后会看到：

```text
工程目录/
├─ CMakeLists.txt
├─ CMakePresets.json
└─ build/
   └─ Debug/
      ├─ CMakeCache.txt
      └─ ...
```

如果 Configure 失败，应先查看 VS Code 的“查看 → 输出”面板，并在右上角选择 `CMake/Configure`，不要只看编辑器中的红色波浪线。

#### 6. Build编译工程

配置成功后，执行：

```text
CMake: Build
```

或者点击 CMake 侧栏中的 Build 按钮；已启用状态栏按钮时也可以从底部操作。CMake Tools 会调用 CMake，再由 CMake 调用 Ninja 等构建工具，最后调用 ARM GCC 完成编译和链接。

编译输出可以在“查看 → 输出”面板中选择 `CMake/Build` 查看。编译成功后，通常在预设指定的构建目录或其子目录中查找生成的文件；如果工程另行指定了目标输出路径，以工程配置为准：

```text
*.elf
*.hex
*.bin
```

通常会生成 `.elf`；`.hex` 和 `.bin` 是否生成取决于工程是否配置了相应的转换步骤。包含符号和调试信息的 `.elf` 文件，是 Orbit 进行源码调试时最重要的文件。

### CMake Tools常用操作

### CMake Tools常见问题

#### 找不到CMake

先在终端执行：

```powershell
cmake --version
```

如果终端找不到 CMake，但 CMake Tools 可以编译，可能是 CMake Tools 使用了 `cmake.cmakePath` 中指定的绝对路径，或者找到了 Visual Studio 等软件附带的 CMake。此时应在 `settings.json` 中明确指定 `cmake.exe` 的完整路径。

#### 命令面板搜索kit没有相关命令

先搜索 `CMake: Select Configure Preset`。如果能找到，说明当前启用了 Presets 模式，应按本教程选择配置预设和构建预设，不需要扫描或选择 Kit。

只有需要维护旧式 Kit 工程时，才在该工程的 `.vscode/settings.json` 中设置 `"cmake.useCMakePresets": "never"`，再按 Kit 模式配置。该设置会停用预设集成，原来写在预设中的工具链、生成器、构建目录等配置需要另行设置，不建议为了让 Kit 命令出现而切换模式。

如果连 `CMake: Configure`、`CMake: Build` 也找不到，应检查 Microsoft 的 CMake Tools 是否已安装并在当前工作区启用，以及打开的文件夹是否包含 `CMakeLists.txt`；必要时重新加载窗口。

#### 工程没有CMakePresets.json

如果工程已经提供 ARM GCC 工具链文件，可以执行 `CMake: Add Configure Preset`，选择 **Toolchain File** 模板并指定该文件，再补充 Debug 配置和构建预设。也可以直接在工程根目录创建 `CMakePresets.json`。

下面是使用 Ninja 的示例，要求 CMake 3.21 或更新版本。示例假定工程已有 `cmake/gcc-arm-none-eabi.cmake`；请将 `toolchainFile` 改为自己工程中实际存在的工具链文件路径，不要覆盖工程已有的预设文件：

```json
{
    "version": 3,
    "configurePresets": [
        {
            "name": "Debug",
            "generator": "Ninja",
            "binaryDir": "${sourceDir}/build/Debug",
            "toolchainFile": "${sourceDir}/cmake/gcc-arm-none-eabi.cmake",
            "cacheVariables": {
                "CMAKE_BUILD_TYPE": "Debug"
            }
        }
    ],
    "buildPresets": [
        {
            "name": "Debug",
            "configurePreset": "Debug"
        }
    ]
}
```

保存后，确认 `cmake.useCMakePresets` 为 `auto` 或 `always`，按前面的步骤选择预设、配置和编译。此示例的命令行等价操作如下，在包含预设文件的工程根目录执行：

```powershell
cmake --preset Debug
cmake --build --preset Debug
```

如果工程连 ARM GCC 工具链文件都没有，应先补齐 STM32 交叉编译配置。只选择 ARM GCC 编译器还不足以配置芯片、启动文件和链接脚本。

预设文件格式参见 [CMake 官方 Presets 文档](https://cmake.org/cmake/help/latest/manual/cmake-presets.7.html)。

#### 预设找不到ARM GCC或Ninja

在 VS Code 新开的终端中执行 `arm-none-eabi-gcc --version`；使用 Ninja 生成器时再执行 `ninja --version`。如果工具链文件使用的是程序名称，确认相关工具已加入 `PATH`；如果使用绝对路径，确认文件中的路径确实存在。修改环境变量后重新打开 VS Code，再配置工程，Kit 扫描不能修复预设中的错误路径。

#### 切换编译器或生成器后配置失败

CMake 会把上一次的配置保存在 `CMakeCache.txt` 中。切换编译器、生成器或 toolchain 后，执行：

```text
CMake: Delete Cache and Reconfigure
```

使用 CMake GUI 和 CMake Tools 操作同一工程时，应确认两者的构建目录、生成器和工具链配置一致。

## Orbit

### 什么是Orbit

Orbit 是运行在 VS Code 中的 STM32 / ARM Cortex-M 嵌入式调试扩展。它可以通过 J-Link 或 CMSIS-DAP/DAPLink 连接目标单片机，并提供源码级调试、断点、单步、Watch、Timeline、RTT 日志和外部 Viewer 接入。

编译工具链和调试工具链是两套不同的工具：

```text
ARM GCC + CMake       → 编译固件，生成 ELF 文件
Orbit + 调试探针     → 下载固件并调试单片机
```

### 准备调试探针

二选一即可：

- **J-Link**：安装 SEGGER J-Link 软件包，使用 J-Link DLL 调试，并可用 `JLink.exe` 烧录；
- **CMSIS-DAP/DAPLink**：连接标准 CMSIS-DAP/DAPLink probe。1.1.0 真机验收为 v1 HID；v2 WinUSB 有代码/Mock，本版未做真机。Orbit 的 VSIX 已包含对应 helper，不需要安装 J-Link 软件，也不使用 OpenOCD/GDB server。

#### J-Link

Orbit 调试需要 SEGGER J-Link 软件包提供的驱动、`JLink_x64.dll` 和可选的 `JLink.exe`。

1. 打开 SEGGER 官方下载页面：

   [SEGGER J-Link 下载页面](https://www.segger.com/downloads/jlink/)

2. 下载并安装 Windows 版本的 J-Link Software and Documentation Pack。

3. 安装完成后，默认情况下相关文件通常位于：

   ```text
   C:\Program Files\SEGGER\JLink
   ```

4. 将 J-Link 通过 USB 连接到电脑，并确认设备驱动安装正常。

#### CMSIS-DAP / DAPLink

1. 将 probe 通过 USB 连接到 Windows，确认设备管理器能看到 CMSIS-DAP/DAPLink 接口；v2 通常使用 WinUSB，v1 使用 HID。
2. 准备与目标 MCU 匹配的 ELF/AXF；默认烧录还需要 Orbit 支持的或用户明确提供且许可可用的 Flash Algorithm。
3. 多个 probe 同时连接时，记录 serial 或 VID/PID，供 `launch.json` 精确选择。

### 安装Orbit扩展

1. 打开 Orbit 的发布页面：

   [Orbit Releases](https://github.com/zhuangyan114/Orbit/releases)

2. 下载对应版本的 `.vsix` 文件，例如：

   > Orbit-1.0.0.vsix

3. 在 VS Code 中按下 `Ctrl + Shift + P`，执行：

   > Extensions: Install from VSIX...

4. 选择刚刚下载的 `.vsix` 文件，等待安装完成，然后重新加载 VS Code 窗口。

5. 在扩展列表中搜索 `Orbit`。如果能够看到 Orbit 扩展，说明安装成功。

### 配置Orbit

安装 Orbit 后，可以按以下步骤验证调试环境：

1. 使用 CMake 和 ARM GCC 编译工程，确保生成了 `.elf` 文件。

2. 使用 J-Link 或 CMSIS-DAP/DAPLink 连接目标单片机。

3. 在 VS Code 中打开包含 `.elf` 文件的工程。

4. 创建或打开 `.vscode/launch.json`，选择 Orbit 提供的 `orbit` 调试器类型；旧配置中的 `ozone` 类型仍可用。

5. 默认 `probe: "auto"` 会先检测 J-Link，再检测 CMSIS-DAP/DAPLink；两者同时连接时始终选择 J-Link。最小配置只填写一次 MCU 型号，Orbit 会使用 SWD / 4000 kHz、自动查找 ELF 和 SVD：

   ```jsonc
   {
     "name": "Orbit Debug",
     "type": "orbit",
     "request": "launch",
     "device": "实际 MCU 型号"
   }
   ```

   要强制使用 DAPLink，在同一配置中增加 `"probe": "cmsis-dap"`；要强制使用 J-Link，增加 `"probe": "jlink"`。本地没有匹配 SVD 时，Orbit 只按需下载并缓存该 STM32 系列的一个 Keil Device Family Pack，从中提取当前芯片 SVD，不会一次下载整个 SVD 库。

6. 启动调试。如果能够连接目标、按配置完成或跳过烧录、加载 ELF 符号并停在源代码中，说明 Orbit、探针和固件已经正常配合工作。

当然,Orbit的 **一切配置** 都可以由ai完成,仅需在你的项目文件夹调用ai,让ai调用 `Releases\Orbit-Config-skill`
